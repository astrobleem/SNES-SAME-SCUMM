# Generic controller across room boundaries

Status: implementation in progress.

The controller’s semantic path is room-neutral: cursor projection, source
CDHD hit testing, authored verb discovery, runtime C17/object-name display,
sentence submission, ACTION_PENDING, and selected-object revalidation do not
use Fate room or object identifiers. Room 68 → room 42 remains an explicit
startup fixture handoff; actor/locker rendering remains fixture presentation
code.

## Boundary contract

The room-installed lifecycle resets selected object/verb, interaction scratch,
pending HUD state, and cursor render cache. The generic frame is inert until
the installed-room lifecycle marks the controller service ready. The reset
does not cancel the normal sentence mailbox.

The FULL ATLANTIS source audit resolves the missing prerequisite to global

These are authored `loadString` operations, not VerbOps metadata. Global
script 144 only reads string 30 with `$27 $44`; global script 145 reads string
31 with the same operation. Global scripts 18 and 132 configure verbs, but
neither creates or loads C8 string 30/31. The prior M23B fixture seed used 153
bytes for each string; that was a bounded historical fixture input, not the
authentic producer or an acceptable replacement here.

The authoritative host boot trace records the lifecycle that reaches this
producer: boot global script 1 starts global 75 at `$050A`, then global 18 at
`$060D`; script 18 starts global 132 and later completes. Script 1 then
continues through the title/game lifecycle. The phase-6 room49 build instead
starts with a scenario room request for room 49 and does not schedule global
script 1. That is the first omitted authored lifecycle step. The resulting
`C8_SIZES[30] = 0` at global 144 is therefore an incomplete scenario-root
state, not a new StringOps or controller defect.

## Phase-6 source-backed mid-game root

Phase 6 intentionally starts after the boot-global lifecycle, so it does not
execute script 1 before global 144. The accepted fixture correction is a
room-install boundary setup that recreates the incoming state authored by the
two script-1 `loadString` records above. It is compiled only when
`SAME_BUILD_SCUMM_SCENARIO_FIXTURE` and `SAME_BUILD_SCUMM_PHASE6LA1D` are
enabled; the production interpreter and StringOps implementation remain
unchanged.

The setup is source-backed, not a StringOps special case: it uses the audited
FULL source values (169 bytes of `$64` for each of IDs 30 and 31) and runs
after the normal C8 reset at room installation. Target evidence is

This is deliberately a mid-game fixture root. A full-game run must still use

## Room49 long-HUD overlay geometry

`Walk to path away from dock` exposed a target-neutral overlay geometry bug.
The producer's glyph bounds reached `CONTENT_X1 = 156` even though the
initialized INDEX8 plane is 80 pixels wide. With the overlay origin at an
unaligned screen position, the backend saw 11 columns by 2 rows (22 unique
cells), then attempted another scan cell before source clipping could reject
it. The 22-cell staging allocation was not intrinsically too small.

The text-service descriptor now clamps content bounds to the initialized
plane: `X0/Y0 >= 0`, `X1 <= 79`, and `Y1 <= 7`. The fix is generic and leaves
tile/staging capacity unchanged. On ROM
`5d1b408c001f5afbe6ef07dfc6775bb78b7c81181ad85212e703008da0fdfa39`, room49
object596's 22 unique cells are accepted, overlay generation 2 commits in
IDLE state with zero errors, and the inspected native capture shows
`Walk to path away from dock`.

## Room49 committed overlay coordinate comparison

The committed failing `Look at salvage boat` capture was not empty text or an
unfinished backend transaction. Its text payload was 20 bytes, its generation
was 2, conversion/DMA completed, and the backend was idle and unlocked. The
committed descriptor was `X=399,Y=84,W=80,H=8`, with clamped content bounds
`X0=0..X1=79,Y0=0..Y1=7`. BG2 consequently projected the descriptor to tile
columns `49..31`; the start was beyond the 32-column tilemap, so no visible
cell range could be realized. This is the first concrete A/B difference from
the accepted object596 overlay, whose committed descriptor was `X=51,Y=50`
with the same bounded raster geometry and 22 in-range cells.

The room49 surface projection is source X `192..447` into native X `0..255`.
The controller's C23 position is produced from the cursor plus its text anchor;
the target-neutral overlay presentation boundary previously subtracted the
virtual-screen center offset but omitted the published surface source crop.
The generic correction now subtracts `SAME_VIDEO_SURFACE_SOURCE_X` there.
For cursor room X `411`, the descriptor becomes `207` after the established
text anchor, inside the native overlay domain, rather than `399`. No
room/object-specific branch was added.
